## 1. RDFLib —— RDF 图处理的"Python 标准库"

### 原理

RDF 的数据模型极简：**一切皆是三元组**（主语, 谓语, 宾语）。一个知识图谱就是一个三元组集合。

```
:sku1  :sales30d  120
:sku1  a          :SKU
:sku1  :belongsToCategory  :cat_running_shoes
```

RDFLib 提供三件事：
- **解析器/序列化器**：Turtle / RDF/XML / JSON-LD / N-Triples 等格式 ↔ 内存图对象；
- **Graph API**：`graph.triples((s, p, o))` 模式匹配（传 `None` 即通配），`graph.value()`、`graph.objects()` 等便捷查询；
- **SPARQL 引擎**：`graph.query("SELECT ...")`，进程内执行，不需要服务器。

内存结构：默认是内存哈希索引（`Memory` store），也支持 BerkeleyDB 持久化。它**不是**生产级图数据库——它是"图的处理库"。

### 实操

```bash
cd ontology-demo
.venv/bin/python - <<'EOF'
from rdflib import Graph
g = Graph().parse("data/catalog.ttl", format="turtle")
print(len(g), "条三元组")

# 模式匹配：找出所有 SKU 的销量
from rdflib import Namespace, URIRef
ECAT = Namespace("https://demo.local/ecat#")
for s, p, o in g.triples((None, ECAT.sales30d, None)):
    print(s.split("#")[-1], "→", o)

# SPARQL
q = """PREFIX : <https://demo.local/ecat#>
SELECT ?sku ?s WHERE { ?sku :sales30d ?s . FILTER(?s > 50) }"""
for row in g.query(q):
    print(row)
EOF
```

### 在项目中的作用

DEMO 里所有的图装载（`kg.py: load_graph`）、CQ 查询、治理检查，底层都是 rdflib。
它是"开发期/中小规模"的完美选择：零部署、可单测、CI 友好。

### 工业级替代

| 替代 | 何时用 |
|---|---|
| **Apache Jena**（Java） | JVM 技术栈、需要 TDB2 持久化、Fuseki 服务端 |
| **RDF4J**（Java） | 需要嵌进 Java 应用、接 Sail 存储抽象层 |
| **Oxigraph**（Rust） | 高性能嵌入场景、二进制分发 |
| **GraphDB/Stardog** | 数据量上亿三元组、需要 ACID、权限、集群 |

经验值：rdflib 处理百万级三元组没问题，千万级以上开始吃力。

## 2. owlrl —— OWL-RL 前向链推理机

### 原理

OWL 2 有三个 Profile（EL/QL/RL）。**OWL 2 RL 的核心思想：把语义翻译成一组"if…then…"产生式规则**，用前向链不断触发直到不动点。

例子——传递性 `subCategoryOf` 对应 RL 规则 `prp-trp`：

```
IF  ?a :subCategoryOf ?b  AND  ?b :subCategoryOf ?c
THEN 推断 ?a :subCategoryOf ?c
```

属性链（`prp-spo2`）：

```
IF  ?sku :isSKUOf ?p  AND  ?p :madeBy ?b
THEN 推断 ?sku :skuBrand ?b      # 本体中声明的链公理
```

owlrl 做的事：读入图 → 反复应用 RL 规则集 → 把推出的新三元组**物化**（写回图里）。
DEMO 里 `kg.reason()` 一行，269 条三元组膨胀出 545 条——多出来的全是推理产物。

**与描述逻辑（DL）推理机的本质区别**：
- owlrl（RL 规则）：**不完备但快**，多项式时间，适合数据密集型；
- HermiT/Pellet（DL tableau 演算）：**完备但可能很慢**，能发现更深层的逻辑矛盾，适合本体开发期做严格检查。

### 实操

```bash
.venv/bin/python - <<'EOF'
from rdflib import Graph
import owlrl

g = Graph()
g.parse("ontology/category.ttl", format="turtle")
g.parse("data/catalog.ttl", format="turtle")
before = len(g)
owlrl.DeductiveClosure(owlrl.OWLRL_Semantics).expand(g)
print("物化新增：", len(g) - before)

# 验证属性链产物
q = """PREFIX : <https://demo.local/ecat#>
SELECT ?s ?b WHERE { ?s :skuBrand ?b }"""
for row in g.query(q):
    print(row[0].split("#")[-1], "→", row[1].split("#")[-1])
EOF
```

### 在项目中的作用

DEMO 的"知识管理"核心：让查询方（CQ、Agent）不用关心推理——**查 `?sku :skuBrand ?b` 就能命中，尽管数据里从没写过这条三元组**。这就是"语义层"的价值：业务关系声明一次，处处可查。

### 工业级替代

| 替代 | 定位 |
|---|---|
| **HermiT / Pellet / Openllet** | 完备 DL 推理机，本体开发期的严格一致性检查（Protégé 内置） |
| **ELK** | OWL 2 EL 专用，百万类级分类层级秒级完成（医学本体 SNOMED 在用） |
| **GraphDB / Stardog 内置推理** | 生产环境首选：物化策略、增量推理、与事务集成都做好了 |
| **规则引擎（Drools 等）** | 业务规则与本体推理分离部署时 |

生产惯例：**开发期用 HermiT 做严格检查，生产期用 RL/EL 物化推理**——DEMO 里 governance 的一致性检查 + owlrl 就是这个分工的雏形。

## 3. pySHACL —— SHACL 校验引擎

### 原理

先理解**为什么需要 SHACL**：OWL 是开放世界假设——"数据里没写"不等于"违规"。
所以 `:sku5` 缺类目，OWL 推理机不会报错（它认为"也许只是还没记录"）。
SHACL 采用封闭世界假设：**Shape 声明"数据应该长什么样"，不满足就是违规**。

SHACL 模型：
- **NodeShape** 绑定目标（`sh:targetClass :SKU`）；
- **PropertyShape** 约束某属性：基数（minCount/maxCount）、类型、取值范围；
- **SPARQL-based constraint**：任意复杂的业务规则用 SPARQL 表达（DEMO 的价保规则）；
- 输出是标准化的 **ValidationReport** 图（focusNode + message + severity），可被程序消费。

pySHACL 是 SHACL 规范的纯 Python 实现，支持与 rdflib 图直接对接，`inference="rdfs"` 参数可以先跑 RDFS 推理再校验（让校验看到推导出的类型）。

### 实操

```bash
.venv/bin/python - <<'EOF'
from rdflib import Graph
from pyshacl import validate

data = Graph().parse("data/catalog.ttl", format="turtle")
shapes = Graph().parse("ontology/shapes.ttl", format="turtle")
conforms, report, text = validate(data, shacl_graph=shapes, advanced=True)
print(text)   # 完整校验报告
EOF
```

动手任务：给 `shapes.ttl` 加一条"毛利率必须在 0~1 之间"的 Shape，把 catalog.ttl 里某个值改成 1.5，重跑看报告。

### 在项目中的作用

品类运营的"自动合规官"：价保、资质、类目完整性这些**硬规则**，从人肉审 Excel 变成机器校验。DEMO 里它同时是 Agent 的护栏工具（`validate_data`）和本体演进的回归闸门（`evolve.approve` 的 SHACL 回归）。

### 工业级替代

| 替代 | 定位 |
|---|---|
| **Jena SHACL / RDF4J SHACL Sail** | JVM 栈、与 Fuseki/RDF4J 存储深度集成（写入时校验） |
| **GraphDB SHACL** | 生产级：事务内校验、性能优化 |
| **TopBraid EDG** | 商业套件：Shape 可视化编辑 + 治理工作流 + 校验服务化 |

生产惯例：SHACL 卡两个位置——**数据入图管道**（ETL 质量门）和 **API 写路径**（等价于 Palantir Action 的 validation）。

## 4. Protégé —— 本体编辑器（已装到 /Applications）

### 原理

斯坦福开源的本体编辑 IDE，本体工程领域的事实标准。底层是 **OWL API**（Java 的本体操作库），内置 **HermiT/Pellet/ELK** 推理机插件。

它能做而文本编辑做不了的事：
- **可视化类层级**：推理后自动重排层级（被推出的 subclass 关系会移位显示）；
- **一键一致性检查**：推理机跑完，不一致的类标红（等价于 `owl:Nothing` 的子类）；
- **DL Query**：用 Manchester 语法直接问"销售大于 50 的 SKU"；
- 让**业务专家**参与建模——这是企业落地的关键，业务不该看 Turtle 源码。

### 实操（用 DEMO 文件）

1. 打开 Protégé → File → Open → 选 `ontology-demo/ontology/category.ttl`；
2. **Entities** 标签页看 Classes / Object properties / Data properties 三栏；
3. 菜单 **Reasoner → HermiT → Start reasoner**：
   - 看 `SlowMovingProduct` 等类层级是否被推理重排；
   - 检查有没有类标红（本体本身应该是一致的）；
4. **Tools → DL Query**：输入 `SKU and (sales30d some xsd:integer[>= 50])` 试试（需要本体里有相应定义，可作为建模练习）；
5. 练习：在 GUI 里给 `:Product` 加一个 `hasPromotion` 属性，保存，然后 `git diff` 看 Turtle 变了什么——理解 GUI 操作和序列化的对应关系。

### 在项目中的作用

DEMO 的 `category.ttl` 是手工写的，真实项目里本体由它编辑维护。**建模阶段的工具**，不进入运行时。

### 工业级替代

| 替代 | 定位 |
|---|---|
| **WebProtégé** | Protégé 的多人在线协作版（斯坦福官方，免费） |
| **TopBraid EDG** | 商业：建模+治理+SHACL+工作流一体，大企业主流 |
| **metaphactory** | 商业：建模+知识图谱应用平台 |

## 5. ROBOT —— 本体工程的 CI 工具链（`tools/robot`）

### 原理

OBO 社区（生物本体开放组织）出品的**命令行本体流水线工具**，定位是"本体界的 Make"：
把本体开发中重复的检查/转换/发布动作变成可脚本化的命令，放进 CI。

核心命令族：
- `robot reason`：调推理机（ELK/HermiT）做分类与**一致性检查**（本体不一致会报错退出）；
- `robot verify`：**自定义 SPARQL 违规查询**做 CI 门禁——查询返回任何结果即判失败，
  用来卡"不允许出现的模式"（如互斥类同实例）；
- `robot report`：跑一套质量检查清单（缺 label、缺定义、循环依赖等），出报告；
- `robot convert`：格式转换（OWL/Turtle/OBO/JSON）；
- `robot merge / extract / diff`：合并、抽取模块、版本对比。

底层同样是 OWL API，可以把它理解成"Protégé 的 CI 版"。

### 实操（用 DEMO 文件，以下命令全部实测通过）

```bash
cd ontology-demo
# Java 位置（brew 装的 openjdk 是 keg-only，手动指一下）
export PATH="/opt/homebrew/opt/openjdk/bin:$PATH"

# ① 一致性 + 分类推理 —— 本体自身（T-Box）必须一致（CI 第一关）
tools/robot reason --reasoner ELK \
  --input ontology/category.ttl --output /tmp/reasoned.ttl
# ✅ 实测通过：本体一致

# ② 抓实例级矛盾 —— 把本体和数据合并后推理，
#    ELK 直接报 "The ontology is inconsistent"（实测抓到了 sku7：
#    同时是 ActiveProduct 和 DelistedProduct，违反 disjointWith）
cat ontology/category.ttl data/catalog.ttl > /tmp/merged.ttl
tools/robot reason --reasoner ELK --input /tmp/merged.ttl --output /tmp/out.ttl

# ③ 质量报告 —— 缺 label、缺定义等（实测：发现我们本体 13 个属性缺
#    rdfs:label，ERROR 级 —— 正好演示质量门的价值）
tools/robot report --input ontology/category.ttl --output /tmp/report.tsv --fail-on none
column -t -s$'\t' /tmp/report.tsv | head -20

# ④ verify —— 自定义违规查询做 CI 门禁：查询有结果即失败（exit 1）
printf 'PREFIX : <https://demo.local/ecat#>\nSELECT ?x WHERE { ?x a :ActiveProduct ; a :DelistedProduct . }\n' > /tmp/violation.rq
tools/robot verify --input /tmp/merged.ttl --queries /tmp/violation.rq --output-dir /tmp/vr
# ✅ 实测：FAIL，输出 sku7 —— 等价于 governance.py 的一致性检查

# ⑤ 格式转换（Turtle → RDF/XML 等，对接只认特定格式的系统）
tools/robot convert --input ontology/category.ttl --format owx --output /tmp/category.owl
```

### 在项目中的作用

DEMO 的 `governance.py` 是 Python 内嵌实现；企业里这一层应该接到 CI：
**每次本体 PR，自动跑 `robot verify + robot report + CQ 回归`**——本体变更 = 代码变更。

## 6. Apache Jena —— SPARQL 全家桶（brew 已装）

### 原理

Jena 是 Apache 的 RDF 生态 Java 框架，四个组件各管一段：

| 组件 | 干什么 | 对应 DEMO |
|---|---|---|
| **riot** | RDF 文件语法校验/格式转换 | 提交前检查 ttl 语法 |
| **arq** | 命令行 SPARQL 查询 | `kg.query()` 的命令行版 |
| **TDB2** | 原生持久化三元组存储 | rdflib 内存图 → 落盘 |
| **Fuseki** | SPARQL HTTP 服务器 | 把图谱变成服务，Agent/应用远程查询 |

**为什么需要 Fuseki**：DEMO 里 rdflib 是进程内的——Agent、前端、其他系统要查图谱就得 import Python。Fuseki 把图谱变成标准 HTTP 服务（`POST /sparql`），任何语言都能查——这是"本体成为平台层"的第一步。

### 实操

```bash
# ① riot：语法校验（CI 里卡 ttl 合法性）
riot --validate ontology/category.ttl && echo "语法OK"

# ② arq：命令行跑 CQ（注意先把阈值占位符替换掉——这活 DEMO 里 governance.py 干）
sed -e 's/$MIN_SALES/50/' -e 's/$MIN_MARGIN/0.15/' -e 's/$AS_OF/2026-08-28/g' \
    cq/cq1_promo_eligible.rq > /tmp/cq1.rq
arq --data data/catalog.ttl --query /tmp/cq1.rq

# ③ 推理后再查（arq 本身不做 OWL 推理，先用 Python 物化）
.venv/bin/python -c "
from kg import KnowledgeGraph
kg = KnowledgeGraph(); kg.reason()
kg.enriched.serialize('/tmp/enriched.ttl', format='turtle')
print('物化图谱已导出')"
arq --data /tmp/enriched.ttl --query /tmp/cq1.rq

# ④ Fuseki：起 SPARQL 服务
fuseki-server --update --mem /ecat &
curl -X POST http://localhost:3030/ecat/update \
  -H "Content-Type: application/sparql-update" \
  --data "LOAD <file://$PWD/data/catalog.ttl>"
curl -G http://localhost:3030/ecat/sparql \
  --data-urlencode "query=PREFIX : <https://demo.local/ecat#> SELECT ?s ?v WHERE { ?s :sales30d ?v }" \
  -H "Accept: application/sparql-results+json"
kill %1
```

### 在项目中的作用

DEMO 的进程内查询 → 企业里的**图谱服务化**。Fuseki 是免费方案里最小的可生产选项。

### 工业级替代

| 替代 | 定位 |
|---|---|
| **GraphDB**（Ontotext） | 商业/有免费版：内置推理+SHACL+全文检索，欧洲企业主流 |
| **Stardog** | 商业：虚拟图+推理+权限最强，Palantir 之外的常见选择 |
| **Amazon Neptune** | 云托管，AWS 栈首选 |
| **AllegroGraph / Virtuoso / QLever** | 各有场景（老牌/开源/超大规模查询） |
| **Neo4j** | 属性图路线（非 RDF），生态最大，但语义标准支持弱 |

选型原则：**需要 OWL 推理 + SHACL 一体的选 GraphDB/Stardog；纯查询性能选 QLever/Neo4j；云原生选 Neptune**。

## 7. Ontop —— OBDA 虚拟化（`tools/ontop-cli`）

### 原理

企业落地的最大阻力：**数据已经在 MySQL/数仓里，不想搬到图库**。
OBDA（Ontology-Based Data Access）的思路：数据不动，**本体盖在数据库上当虚拟视图**。

```
SPARQL 查询  ──►  Ontop  ──►  按 R2RML 映射改写为 SQL  ──►  MySQL/PG
     ▲                                                        │
     └──────────────  结果包装回三元组形式  ◄────────────────┘
```

核心技术是 **查询重写（query rewriting）**：利用本体的类层级和映射规则，把一个本体级的
SPARQL 展开成等价的 SQL UNION 查询。这是 OWL 2 QL Profile 的设计初衷（可一阶逻辑重写）。

### 实操

Ontop CLI 需要 JDBC 连接真实数据库。最小练习（H2 内存库）：

```bash
cd ontology-demo/tools/ontop-cli
# 1. 写一个 H2 建库脚本（模拟商品中台的 sku 表）
# 2. 写 R2RML 映射文件 mapping.ttl：
#    "sku 表的行 → :SKU 实例，SALES_30D 列 → :sales30d 属性"
# 3. 起虚拟 SPARQL 端点：
./ontop endpoint --ontology ../../ontology/category.ttl \
  --mapping mapping.ttl --properties db.properties
# 4. 浏览器/curl 查 http://localhost:8080/sparql —— 查的是本体，跑的是 SQL
```

Ontop 还有 **Protégé 插件**：在 Protégé 里直接编辑映射并测试查询（`tools/` 里没装，
从 Ontop release 页下 `it.unibz.inf.ontop.protege-*.jar` 放进 Protégé 插件目录即可）。

### 在项目中的作用

DEMO 的数据是手写 Turtle；真实项目这一步换成 Ontop 映射到商品中台 MySQL——
**本体层不动、CQ 不动、Agent 不动，只是数据来源从文件变成数据库**。
这正是"本体即平台层"的解耦价值。

### 工业级替代

| 替代 | 定位 |
|---|---|
| **Stardog Virtual Graphs** | 商业虚拟化标杆，支持几十种数据源 |
| **Denodo** | 通用数据虚拟化平台（非本体专用，但企业已有率高） |
| **Ultrawrap** | 学术转商用，R2RML 高性能 |
| **直接物化（ETL 入图库）** | 查询性能优先时的主流选择，代价是数据双份 |

## 8. 四条贯穿性原则（所有工具之上的）

1. **标准优先**：Turtle/OWL/SHACL/SPARQL/R2RML 全是 W3C 标准——DEMO 里换任何一层
   其他层都不用动，这就是标准的意义。企业选型时"是否符合标准"比"功能多"重要。
2. **开放世界 vs 封闭世界分工**：OWL 推理机管"能推出什么"，SHACL 管"数据合不合规"，
   永远别拿 OWL 约束当非空校验用。
3. **开发期严格、生产期宽松**：建模用 HermiT 完备推理找矛盾；生产用 RL/EL 物化推理
   保性能。两套推理不是冗余，是不同阶段的质量门。
4. **本体变更 = 代码变更**：Git 版本化 + PR review + CI 回归（robot verify + CQ 测试 +
   SHACL 基线对比）+ 审计日志。DEMO 的 `evolve.py` 就是这个流程的最小实现。

## 9. 一页速查：DEMO 代码 ↔ 工具原理

| DEMO 代码 | 底层工具 | 原理 |
|---|---|---|
| `kg.py: load_graph()` | rdflib parser | Turtle → 内存三元组集合 |
| `kg.py: reason()` | owlrl | OWL-RL 产生式规则前向链，物化到不动点 |
| `kg.py: validate()` | pyshacl | Shape 匹配 + 封闭世界约束检查 |
| `governance.py: check_consistency()` | SPARQL 查询 | disjoint 矛盾的主动检测（替代 DL 推理报错） |
| `governance.py: cq_regression()` | rdflib SPARQL | 胜任力问题 = 本体的单元测试 |
| `evolve.py: detect_gaps()` | 命名空间对比 | 数据信号 vs 本体声明集合的差集 |
| `agent.py: compile_ontology_context()` | rdflib 元数据查询 | 本体 → LLM 系统提示词 |
| `agent.py: make_tools()` | Kimi tool calling | 本体治理的能力面暴露给 Agent |
